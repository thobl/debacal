What is already working

  • Navigation sits beside the period; View, Selection, and Events have distinct semantic groups.
  • Segmented controls communicate one choice within each group.
  • Calendar creation target and visibility are separate. Search has stable space in the sidebar.
  • Selection keeps the calendar’s hue, using a border and a vertical bar. All-day events span days.

Where I would refine it

  • Readability first. Some hour labels, secondary text, and light-colored event text are too faint.
  • A calmer hierarchy. Give the current period priority over branding, then event titles over metadata.
  • More deliberate spacing. Use smaller gaps within groups and larger gaps between them; remove redundant boxes.
  • Consistent states. Keep source color, selected events, chosen controls, and keyboard focus visually distinct.

Why the color treatment matters

The current event painter derives text color from the calendar color. That works for some calendars but breaks down for light colors. All three proposals retain the source hue while choosing dark text independently.

Design principles and sources
  • Nielsen Norman Group · Proximity — spacing communicates which controls belong together, including when a layout wraps.
  • Nielsen Norman Group · Similarity — consistent appearance for consistent roles; distinct treatments for actions and exclusive choices.
  • GNOME HIG · Typography — use the desktop font and a small set of meaningful type roles rather than many tiny styles.
  • GNOME HIG · Principles — respect attention, make frequent actions easy to reach, and disclose complexity when needed.
  • W3C · Text contrast and non-text contrast — useful readability benchmarks for text, focus, and essential indicators.
  • W3C · Use of color — source colors are helpful, while selection and visibility still need recognizable shapes or controls.

GNOME guidance informs the desktop design review; the proposals remain Qt. The prototypes reuse existing icons and workflows rather than introducing a separate UI framework.

How to judge the examples
  1. Compare A, B, and C at full size. Which feels most comfortable for daily use?
  2. Check the smaller window: B’s extra row costs vertical calendar space; C’s larger text truncates more long titles.
  3. Switch to bright yellow: event titles, times, and the selected outline should remain readable.
  4. Check Month and Import: the visual language should carry across, while date inclusion remains clear.

My starting recommendation is A’s restrained layout and warmth, combined with C’s neutral event text and lighter card fills. B is an alternative if the date-and-view relationship should be stronger. These choices can be mixed; they are not three all-or-nothing redesigns.

These are static rendering experiments. They do not demonstrate changed interactions, dark mode, all languages, every display scale, or complete accessibility conformance. Long-title clipping and the existing import-date selection behavior are preserved for honest comparison.
